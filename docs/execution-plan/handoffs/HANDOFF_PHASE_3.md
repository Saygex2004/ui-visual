## 2. Notes, observations, implementation details

- **Playwright's `globalSetup` runs *after* `webServer` processes are started and healthy, not before** — the opposite of what the config's own original comment assumed, and the opposite of what seemed like the natural reading of "global setup." Verified directly in `playwright@1.61.1`'s source (`createGlobalSetupTasks` in `lib/runner/index.js`): the task order is `removeOutputDirs → plugin setup (this starts every webServer and waits for its health check) → globalTeardowns → globalSetups`. A `globalSetup` that wipes `users`/`usernames`/`sessions` to force a fresh bootstrap therefore runs **after** the API server already booted and bootstrapped an admin — deleting that admin before any test can log in, indistinguishable from the outside from "bootstrap never ran" (both produce `errors.auth.invalidCredentials` on the correct password). **Fix:** moved the wipe into the server's own boot sequence instead of Playwright's lifecycle, gated behind a new env var `PVPDASH_RESET_ACCOUNTS_ON_BOOT` (`apps/server/src/config.ts`, consumed in `index.ts` immediately before `buildApp`) so the ordering is guaranteed by being sequential code in one process. `playwright.config.ts`'s API `webServer` sets it; `e2e/global-setup.ts` was deleted (`globalSetup` removed from the config entirely — it had no other purpose). Documented in `CONFIGURATION.md` §3 and `.env.example`, explicitly never set outside the e2e webServer.
- **`apiClient.ts` always sent `Content-Type: application/json`, even on bodyless POSTs** (`/auth/logout` takes no body) — and Fastify 5's default JSON body parser explicitly rejects a zero-length body under that content-type (`FST_ERR_CTP_EMPTY_JSON_BODY`, HTTP 400: *"Body cannot be empty when content-type is set to 'application/json'"*, `fastify/lib/content-type-parser.js`). This is a **real application bug, not a test artifact** — any real user clicking "Esci" would have hit the same 400 and silently failed to sign out (the mutation's `onError` isn't wired to show anything for logout, so it would have looked like a dead button). Fastify's `.inject()` (used by the integration suite) never reproduced it because the existing logout test never set a `Content-Type` header on a bodyless request — only a real `fetch()` from the browser does that by default. Only e2e caught it. Fixed by only attaching the header when a body is actually being sent (`apps/web/src/lib/apiClient.ts`). **Takeaway for later phases:** the integration suite's HTTP-level coverage and a real-browser e2e path are not redundant — this class of bug (header/parser interaction) is invisible to `.inject()`.
- **Two Vite dev-server bugs**, both silent until exercised through a real browser:
  - Vite's default dev bind is IPv6-only; `curl http://127.0.0.1:5173` (and Playwright's `webServer` health check, which uses `127.0.0.1`) got connection-refused despite Vite reporting itself ready. Fixed with an explicit `server: { host: '127.0.0.1' }` in `apps/web/vite.config.ts`.
  - The dev proxy's `rewrite` stripped the `/api` prefix before forwarding to the API server — but the API server registers every route **under** `/api` itself (mirroring how Firebase Hosting rewrites preserve the prefix in production), so every browser request 404'd while curl against the API server directly kept working (curl bypasses the proxy). Fixed by removing the `rewrite` entirely; the proxy now forwards `/api/*` verbatim.
- **i18next namespace/key double-prefixing.** Server error envelopes carry a full dotted key like `"errors.auth.invalidCredentials"`. Calling `t(key, { ns: 'errors' })` looks for that whole string *inside* the `errors` namespace — i.e. a top-level `errors` key inside `errors.json`, which doesn't exist (the file's top-level keys are `auth`/`admin`/`common`). It silently fell through to `defaultValue` every time, which made the *next* bug (the logout 400 above) harder to see at first because every server error rendered as the same generic fallback text regardless of what actually went wrong. Fixed with a small helper, `translateApiError(t, err, fallback)` (`apps/web/src/lib/translateApiError.ts`), that rewrites the leading `errors.` to `errors:` (i18next's namespace separator) before calling `t()`; applied at all 4 error-handling call sites. **Lesson for later phases writing new error UI: always go through `translateApiError`, never call `t()` directly on a server error key.**
- **PrimeReact 11 is a full architecture break from v9/v10**: `Message`, `Select`, `DataTable` (no `<Column>` anymore), and `Dialog` are compound/headless components with no flat prop API. Only `InputText`, `InputPassword`, `Button`, and `RadioButton(Group)` have simple/flat-ish APIs. **`Button` has no `label` or `loading` prop** — content must be children; a `loading` prop is silently forwarded straight to the DOM as an unrecognised attribute (React logs "Received `false` for a non-boolean attribute `loading`") rather than erroring, so it's easy to miss without visually/structurally inspecting the rendered button — caught here via an e2e failure showing a button with no accessible name at all. Fixed across `LoginScreen`, `ForcedPasswordChange`, `CreateUserForm`, `AccountRow`: text moved to children, `loading` dropped, `disabled` kept as the only pending-state prop. **Scope decision, deliberate:** this phase uses plain semantic HTML + the existing CSS design tokens for the accounts table, alert/message banners, and confirmations (`window.confirm()`) instead of PrimeReact's `DataTable`/`Message`/`Dialog` — proportionate for this phase's needs, and defers researching the compound `DataTable` API to **Phase 4**, which actually needs virtualization for the listings table. Whoever picks up Phase 4 should budget explicit research time for `DataTable`'s v11 API before estimating that phase — it is not a drop-in from any v9/v10 memory or from mid-training-data patterns.
- **Playwright `getByLabel` does substring, case-insensitive matching by default.** `getByLabel('Nuova password')` (no `{ exact: true }`) also matched "Conferma nuova password" (a strict-mode violation — two elements). Every `getByLabel` call whose text is a substring of another visible label on the same screen needs `{ exact: true }`; the existing `getByLabel('Password', { exact: true })` calls already followed this, the two "Nuova password" ones didn't. Fixed in `e2e/auth-flow.spec.ts`.
- **A `page.goto()` immediately after a `.click()` that triggers an async SPA login is a race**, not an auto-waited sequence: Playwright's `.click()` only waits for the click's own actionability, not for whatever asynchronous mutation/navigation the click's handler kicks off (there's no full-page browser navigation for Playwright to auto-wait on — it's a `fetch()` inside React state). The original test 3 did `click('Entra'); goto('/admin')` back-to-back and intermittently landed back on `/login` because the hard reload could beat the login POST's cookie to the browser. Fixed by replacing the hard `goto` with the same SPA menu-click pattern the test already used correctly for sign-out (`getByRole('button', {name: 'admin'}).click(); getByRole('menuitem', {name: 'Amministrazione'}).click()`) — a `.click()` on a locator that doesn't exist yet auto-waits for it, so this naturally rides out the login mutation instead of racing it, and is closer to what a real user does anyway.
- No conflicts with the Specifications were encountered; no delete-account route was added ("accounts are never deleted", `DATA_MODEL.md` §9); no Firebase Auth was introduced.

- **Auth plugin decorator surface** (`apps/server/src/plugins/auth.ts`) — how later modules read the current account: `request.user?: UserPublic` (`id`/`username`/`role`/`must_change_password`, never the password hash) and `request.sessionHash?: string` (sha256 of the session token; needed only by routes that target/preserve the *current* session, e.g. self password-change). Both are set by the shared `preHandler` hook once a request passes the session check; both are `undefined` on `config.auth.public` routes.
- **Every new route from here on must declare `config: { auth: {...} }` explicitly** — there is no implicit-open default anymore (that's what this phase closed). Three flags, composable: `public: true` (no session at all — currently only `/auth/login`; health routes are outside the `/api`-prefixed encapsulation so they're unaffected by this hook entirely), `allowMustChange: true` (session required, but exempt from the forced-password-change gate — currently `/auth/me`, `/auth/password`, `/auth/logout`; nothing else), `role: 'admin' | 'user'` (checked after the must-change gate). A route with none of these requires a session, a *not*-must-change account, and any role — that's almost certainly not what a genuinely public or admin-only route needs, so pick deliberately.
- **New env var:** `PVPDASH_RESET_ACCOUNTS_ON_BOOT` (`0`/`1`, default `0`) — wipes `users`/`usernames`/`sessions` before bootstrap runs. Set only by the e2e `webServer` env; never in dev or production (`CONFIGURATION.md` §3, `.env.example`).
