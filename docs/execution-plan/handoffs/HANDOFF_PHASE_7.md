## 2. Notes, observations, implementation details

- **The Storage emulator cannot sign URLs without real-shaped credentials — a genuine, non-obvious infrastructure gap.** `getSignedUrl()` always calls into `@google-cloud/storage`'s real Application Default Credentials signing path; reading `signer.js` directly confirms there is no emulator-aware branch at all, regardless of `FIRESTORE_EMULATOR_HOST`/`FIREBASE_STORAGE_EMULATOR_HOST`. Fixed with a throwaway RSA keypair (`emulatorSigningCredential`, exported from `seed/lib.ts`) passed as `credential: cert(...)` to `initializeApp()`, **only** when `FIRESTORE_EMULATOR_HOST` is set. This had to be applied in **two** independent call sites — `apps/server/src/firestore.ts`'s `ensureApp` and `seed/lib.ts`'s own `connectDb` — because both race to be the first to actually call `initializeApp()` for the process-global default Firebase app, and whichever wins determines which credential (if either) takes effect. A fix applied to only one of them silently doesn't take effect depending on execution order (integration tests hit `connectDb` first via `testDb()`; a real server boot hits `ensureApp` first). `storage.ts`'s `getBucket()` additionally always passes an explicit bucket name rather than trusting the app's own default, for the same "which init call won" robustness reason.
- **Mark-as-read happens on every `GET`, not just the first open.** UI §6.2 says opening a thread marks it read, but the thread also polls every ~7.5s while open (`POLL_CADENCES_MS.openThread`) — if only the *first* open marked read, the counter would climb while a user is actively looking at the thread. `openOrPollThread` therefore updates `reads/{callerId}.last_read_at` and decrements the caller's counter by exactly the count of others' messages since the old `last_read_at`, on **every** call, but only actually writes to Firestore when there's a real join to perform or a non-zero delta to apply — a no-op poll stays pure-read. Verified end-to-end by a from-scratch "ground truth" recomputation (`computeTrueUnread`, independent of the application code) after a scripted multi-user/multi-thread storm — see the integration test.
- **`RichTextRenderer.tsx` is a hand-rolled recursive component, not a second live TipTap/ProseMirror instance per message** — a deliberate deviation from the most literal reading of "TipTap for compose and render". Mounting one full editor (with its own DOM-sync machinery) per message in a long thread is real, avoidable overhead; TipTap earns its cost in the single interactive Composer instance, not in read-only display. The renderer never re-sanitizes — it renders exactly the already-sanitized allowlisted shape, trusting the server, same as any other rendering of stored data in this app.
- **Two schema enrichments beyond the original API_CONTRACT.md, both to avoid a forbidden cross-feature import**: `UserRefSchema`/`author_username`/`participants: UserRef[]` (server-side id→username resolution, mirroring Phase 6's `ActivityEventView.actor_username` precedent — `GET /admin/users` is admin-only, so a regular participant has no other way to resolve a colleague's name) and `ListingSummarySchema` embedded directly in `ThreadView`/`ThreadListItem` (raw facts, never composed prose, per DATA_MODEL.md §2 — otherwise `features/chat/` would need to reach into `features/workspace/`'s data layer, which FRONTEND.md §1 discourages).
- **One new endpoint not in the original contract**: `GET /chats/:listingId/participant-candidates` (any authenticated user, not admin-only) — UI §6.2 lets any participant add a colleague, but the only existing id→username listing path (`GET /admin/users`) is admin-only. Scoped per-thread (excludes existing participants and disabled accounts) rather than a bare `/users`, to avoid exposing more surface than needed. Recorded here per 00_OVERVIEW.md §5 (Part B/API-surface additions are this project's own discretion, provided they're documented).
- **`@fastify/multipart`'s `throwFileSizeLimit` defaults to `true`** — exceeding `limits.fileSize` throws its own `RequestFileTooLargeError` from `file.toBuffer()` rather than silently truncating, which the generic error handler doesn't map to anything (falls through to `errors.common.unknown`). Fixed with a try/catch around `file.toBuffer()` that recognizes `app.multipartErrors.RequestFileTooLargeError` and throws the app's own `ApiError(413, 'errors.attachments.tooLarge')`. Verified by reading the plugin's actual compiled source, not assumed from its type comments.
- **A real e2e cross-file collision, caught by running the full suite, not just the new file**: `chat-collaboration.spec.ts` originally reused listing 1055 (Pisa) — the same row `ratings-collaboration.spec.ts` targets — reasoning that rating state and chat state are disjoint. They're disjoint in the *UI*, but not in the underlying data: both features append to the same per-listing `listing_activity` timeline (`thread_opened`/`attachment_added`/`thread_closed`/`thread_reopened` vs. `rating_set`/`rating_cleared`), and `ratings-collaboration.spec.ts` asserts an **exact** `.workspace-timeline-item` count on that listing's Storico tab. Running the full `pnpm e2e` suite (not just the new file in isolation) surfaced this immediately — 6 items instead of the expected 2. Fixed by moving the chat test to listing 1031 (Tivoli, Roma), confirmed via a real booted snapshot query to be untouched by every other spec file. **Lesson for future phases: always run the full e2e suite before declaring a new spec file done, even when the new listing "shouldn't" interact with existing ones — shared per-listing activity logs are an easy thing to overlook.**
- **No new client-side unit tests for the chat feature** — a deliberate scope call flagged as non-blocking in the phase plan itself ("se il tempo lo permette"). The two `chat-collaboration.spec.ts` e2e tests exercise the real `RichTextEditor`/`Composer`/`MessageList`/`ParticipantList`/`ThreadView` components against a real running server end-to-end (including the sanitizer round-trip), which is what the plan judged sufficient. If a future phase touches this code and wants faster, isolated feedback, component-level RTL tests are the gap to fill first.
- **Minor, non-blocking cosmetic note**: `previewExcerpt`'s plain-text extraction (`extractPlainText`, shared with the `PVPDASH_MESSAGE_MAX_CHARS` check) concatenates block-level children (paragraphs, list items) with no separator, so a `*Le mie chat*` preview line for a multi-block message reads as one run-on string (e.g. "...sottolineata.Verifica editorVerifica allegati..."). Cosmetic only — the stored/rendered message itself is correct everywhere else (proper paragraph/list breaks). Not fixed this phase because `extractPlainText` is a small, already-tested pure function serving two purposes (excerpt **and** the char-limit check), and changing its output shape wasn't in scope; worth a look if `*Le mie chat*` polish comes up later.
- **`jsx-no-literals`/unused-directive lint housekeeping**: bare toolbar glyphs (`B`/`I`/`•`/`1.`/🔗) all wrapped in `{'...'}` expression containers per the established Phase 4-6 precedent; one stray `// eslint-disable-next-line no-alert` left over in `ThreadView.tsx` from drafting was removed (the rule isn't configured in this project, so the directive was flagged as unused — `window.confirm` needs no suppression here, same as Phase 5's *Svuota archivio*).
- No conflicts with the Specifications found or recorded this phase.
