## 2. Notes, observations, implementation details

- **A load-bearing correction to my own plan, caught by the axe pass rather than assumed fixed by the OKLCH formula alone**: the plan's dark-mode token table was computed and verified against WCAG AA before writing any CSS (culori-cross-checked, see the Phase 9 handoff's precedent for not trusting a single hand-rolled contrast calculation) — but the **light**-mode anchor was inherited unchanged from Phase 0 on the assumption that "unchanged" meant "already fine." It wasn't: `--color-accent-contrast` (button text, 99% L, essentially white) on `--color-accent` (58% L) measured **4.26:1** against WCAG AA's 4.5:1 floor for normal-size text — a real failure that had been shipping since Phase 0, surfaced by every primary button on every screen, and only actually caught because this phase ran a real axe pass rather than treating "the formula says the dark pairs are fine" as covering the light ones too. Fixed by moving `--color-accent` (and `--color-focus`, which mirrors it) from 58%→55% L — 4.83:1, comfortably clear, and a 3-point L shift reads as imperceptible, not a hue change. `--color-accent-strong`/`--color-accent-soft`/`--color-accent-contrast` untouched. Re-verified with a second full axe pass after the fix: 0 violations across all 22 screen/theme combinations, versus 6 failing on `color-contrast` before it.
- **A second, unrelated pre-existing defect surfaced the same way**: `landmark-no-duplicate-main`/`landmark-main-is-top-level`/`landmark-unique`, present on the landing screen in *both* themes (so not a dark-mode regression) — `LandingScreen.tsx` had its own `<main>` nested inside `Shell.tsx`'s `<main className="shell-content">`. Confirmed via `git blame`-equivalent reasoning (neither file's `<main>` element appears in any Phase 9 or Phase 10 diff) that this predates this phase entirely; fixed anyway since it's a one-line, zero-risk semantic correction, not deferred to Phase 11 the way a larger a11y remediation would be.
- **The `StatusDisplay` migration scope grew slightly beyond the plan's own enumeration, for the reason the plan itself gave for doing the migration at all**: `.auth-error` (`LoginScreen`/`ForcedPasswordChange`) and `.chat-composer-error` (`Composer`) weren't in the phase plan's explicit "`~10 files`" list, but they're the exact same bespoke-error-text pattern every other migrated site was — an oversight in the plan's own enumeration, not a deliberate exclusion. Migrating them was the obviously-consistent choice once found, and low-risk (message text unchanged, `role="alert"` preserved).
- **Two genuinely unstyled native `<select>` elements were a real, demonstrable inconsistency**, not a hypothetical one: `admin.css` had zero rules targeting `<select>` before this phase — the three admin calendar-assignment tabs' user-picker dropdowns rendered as bare, unthemed browser controls next to fully-styled `TextInput`/`Button` siblings in the same form row. This is exactly the kind of "surface built phase-by-phase, under-designed in spots" gap the phase document's own preamble describes; found by reading every feature's CSS file in full during its redesign pass, not assumed absent.
- **Native `<select>`/`<input type="checkbox">` restyling was deliberately bounded**: selects got border/radius/height/focus-ring parity with `TextInput` (a safe, purely-additive CSS rule), but no `appearance: none` + custom-dropdown-arrow treatment was attempted — that's a materially bigger, higher-browser-risk undertaking (custom arrow icon, cross-browser `<option>` styling limits) disproportionate to this phase's scope. Checkboxes were left as native browser default throughout (admin tables' row-select checkboxes, category checkboxes) — common practice even in fully-designed systems, and reskinning them wasn't named in the phase brief.
- **The Tabs "only the active tab's children mount" invariant from Phase 9 was not re-touched or re-verified this phase** — no Tabs.tsx/AreaView.tsx/ClusterSection.tsx logic changed, only CSS/tokens, so Phase 9's DOM-row-count finding still holds; not re-measured here since nothing that could affect it changed.
- **Dark-mode verification tooling was deliberately kept disposable**: the `@playwright/test`-library-API + a locally-downloaded `axe-core` bundle script lived only in the working tree during this session (never added to `apps/web/package.json`, never committed) — building a permanent visual-regression/axe pipeline is explicitly Phase 11's job (its own carry-over note below flags this), and standing one up here would have been the kind of scope creep the plan's own verification section warned against.

3. **A real, previously-invisible accessibility bug found and fixed: workspace-panel focus-restore-on-close was completely broken.** Radix's `DialogContentModal` *always* overrides `onCloseAutoFocus` to call `event.preventDefault()` then `context.triggerRef.current?.focus()` — and `triggerRef` is only ever populated by a `<Dialog.Trigger>`, which this app never renders (the panel opens via router navigation from a table row's "Scheda"/"Chat" link, not a same-tree trigger click). With no trigger ref, that default handler silently did nothing, and because it had already called `preventDefault()`, FocusScope's own generic restore-to-previously-focused-element fallback never got to run either — focus dropped to `document.body` on every close. Confirmed via a live `focusin`/`focusout` Playwright listener before the fix (no restore event at all) and after (correct `focusin → A.data-table-action-link "📄 Scheda"`). Fixed in two parts: `DataTable.tsx`'s row-action `<Link>`s now call `e.currentTarget.focus()` explicitly on click (TanStack Router's own `handleClick` calls `preventDefault()`, which can suppress native click-to-focus in some cases), and `WorkspacePanel.tsx` captures the pre-mount `document.activeElement` in a lazy `useState` initializer (evaluated during first render, before any effect — including FocusScope's own — can move focus) and restores it explicitly via its own `onCloseAutoFocus`.
4. **A second real, previously-invisible layout bug found and fixed, this time via an e2e failure rather than a live check**: making `.shell-content` a flex column (needed for item 1's vertical centering) silently broke `.area-view`'s width containment. `.area-view` uses `max-width: 90rem; margin: 0 auto` to center itself — but per the flexbox spec, an item's cross-axis *auto* margins (`margin: 0 auto` in a column-direction container) **disable `align-items: stretch`** for that item, so instead of being clamped to the container's width, `.area-view` grew to its own preferred size, up to `max-width` (1488px with padding), regardless of the actual viewport. At any viewport narrower than 1488px this pushed the archive header's `justify-content: space-between`-positioned "🗑️ Svuota archivio" button off-screen to the right — caught by `session-archive.spec.ts`'s `clickExpectingDialog` timing out with "element is outside of the viewport" (root-caused by instrumenting the test with a throwaway `getBoundingClientRect()` debug probe against the ancestor chain, not guessed: `.area-view` measured 1488px wide inside a 1280px viewport). Fixed by adding `box-sizing: border-box; width: 100%;` to `.area-view` (and, for the same underlying reason, to every other `margin: 0 auto` + `max-width` root container that shares this pattern under the now-flex `.shell-content`: `.landing-screen`, `.admin-screen`, `.calendar-month-view`/`.calendar-day-view`, `.chat-standalone-page`, `.chat-my-chats` — only `.area-view`'s 90rem max-width happened to exceed the e2e viewport's 1280px, but the same bug was latent in all of them and would surface on any narrower viewport, including the 320–768px widths a systematic mobile pass would exercise). No `box-sizing: border-box` global reset exists anywhere in this project, so `width: 100%` alone (without `box-sizing: border-box`) would have re-introduced a smaller overflow via padding — verified, not assumed, before committing to the fix.
