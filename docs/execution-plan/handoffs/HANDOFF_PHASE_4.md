## 2. Notes, observations, implementation details

- **PrimeReact 11's `DataTable` has no virtualization story at all** — confirmed by reading the installed package directly: `primereact/datatable`'s only export is ~30 headless sub-parts (`Root`/`TableContainer`/`Row`/`Cell`/…) plus a `useDataTable` state hook; `primereact/virtualscroller` does not exist anywhere in the installed `primereact@11.0.0` tree or in `pnpm-lock.yaml`. `FRONTEND.md` §4's literal "PrimeReact `DataTable` with `virtualScroller`" is therefore impossible to follow as written in this version — not merely inconvenient. Built instead: plain semantic HTML (`<table>`, explicit ARIA roles since `display:flex` rows can strip a browser's implicit table semantics) + `@tanstack/react-virtual`'s `useVirtualizer` for row windowing. This is a deliberate deviation from the phase document's letter, permitted under `00_OVERVIEW.md` §5 (the actual behavioural contract — UI §11 — is explicit that "the requirement is the responsiveness, not any particular technique") and recorded here per that rule. Mirrors Phase 3's own precedent of preferring plain HTML+tokens over PrimeReact's compound APIs when the payoff isn't there.
- **PrimeReact's `Tabs` (`Root`/`List`/`Tab`/`Panels`/`Panel`) is the one place this phase used PrimeReact's compound API directly**, for the cluster nav and bucket tabs — its surface is small (8 parts, not 30), and it gives correct `role="tablist"`/`role="tab"`/`aria-selected` semantics "for free," which is exactly UI §11's explicit accessibility ask. `lazy` mode (`TabsRoot lazy`) is what makes only-the-active-panel-mounts work — confirmed empirically (24 rendered rows, not thousands, when only one cluster's table should be live). **Import gotcha:** `primereact/tabs`'s namespace re-export (`import { Tabs } from 'primereact/tabs'`) does **not** rename members the way `primereact/datatable`'s does (`DataTableRoot as Root`) — `Tabs.parts.d.ts` keeps the full `TabsRoot`/`TabsList`/`TabsTab` names. Direct named imports (`import { TabsRoot, TabsList, TabsTab, TabsPanels, TabsPanel } from 'primereact/tabs'`) are what's actually used here; don't assume the two compound families share a re-export convention.
- **`Select` and `InputNumber` are also fully compound in v11** (confirmed the same way — no flat component, only `*.parts.d.ts` sub-exports), so the toolbar's 4 column choosers are plain `<select>` and the value range is plain `<input type="number">`, styled with tokens. A single-choice dropdown or a numeric input gets nothing from ~14 headless parts that the native element doesn't already provide for free.
- **TanStack Router's `from:` string differs between hook families for a pathless-layout-nested route.** `protectedRoute` is a pathless layout (`id: 'protected-layout'`, no `path`) — its children's **route ID** (not their URL) is prefixed with that id. `useParams({from: ...})` and `useSearch({from: ...})` need the **prefixed** id (`/protected-layout/aste/$area`), confirmed via the exact TypeScript union `tsc` reported; `useNavigate({from: ...})` needs the **unprefixed** path (`/aste/$area`) — the two hook families resolve `from` against different string spaces. Discovered by reading the actual compiler error's full union type rather than guessing; cost real time, worth flagging so the next session doesn't rediscover it. `<Link search={...}>` to a route whose search schema has any non-optional-at-the-type-level field (i.e. a `.catch()`-defaulted field, which is required in the *output* type even though it self-heals on bad input) needs that field supplied explicitly (`search={{ cluster: 1, tab: 'principali', dir: 'asc' }}`, matching the schema's own defaults) — `search={{}}` alone does not typecheck.
- **`react/jsx-no-literals` (default config, `noStrings: false`) only flags bare `JSXText` nodes** (literal text directly between tags, outside any `{}`), not string literals living inside a JS expression container (`{condition ? ' ▲' : ' ▼'}` is fine). The one real violation this phase hit was a literal `" / "` separator sitting bare between two `{}` blocks in `AreaHeader.tsx` — fixed by moving the whole compound string into one interpolated i18n key (`area.metadata.analyzedValue: "{{stored}} / {{total}}"`) rather than assembling fragments in JSX, which is also better i18n practice independent of the lint rule's exact leniency.
- **`snapshot.clusters` always contains one entry per cluster definition, even empty ones** — confirmed in `apps/server/src/cache/build.ts`: the `blocks` Map is pre-seeded from `REAL_ESTATE_CLUSTERS`/`CREDITS_CLUSTERS` before any listing is placed. This is what makes it safe to build the cluster nav and the `TabsPanels` from `snapshot.clusters` directly (one array, one source of truth) instead of importing the static cluster constants a second time and hoping the two never diverge.
- **UI §4.1's asset-type column header wording adapts by table kind** ("Tipo di immobile" vs "Tipo di bene") even though both read the same `tipo_bene` field — easy to miss since it's one field feeding two different header keys; `columns.tsx` has two column defs (`TIPO_IMMOBILE`, `TIPO_BENE_CREDITS`) differing only in `headerKey`, selected by `getColumns(kind)`.
- **`PVPDASH_SEED` was documented since Phase 0 (`CONFIGURATION.md` §3, `.env.example`) but never implemented until now.** Implemented as `seedContent(db)` (`seed/lib.ts`) — deliberately **narrower** than the full `seedAll` (listings/omi_prices/meta/runs/settings only, no accounts) so it composes safely with Phase 3's `PVPDASH_RESET_ACCOUNTS_ON_BOOT` regardless of which runs first at boot; the two flags together are what let `dashboard-browse.spec.ts` get both a real admin session and real listing data from one server boot. Updated `CONFIGURATION.md`/`.env.example` to describe what it actually does now, since the original text ("run the seed script's fixtures," implying the full set) predates this decision.
- **Two Playwright spec files sharing one bootstrapped server means a mutable shared "admin" account** — `auth-flow.spec.ts` rotates the bootstrap admin's password as part of its own flow; `dashboard-browse.spec.ts` only needs *some* signed-in session, not to test the bootstrap flow itself, so it doesn't know or care what "admin"'s current password is. Fixed with a small resilient login helper (try the bootstrap password, fall back to the known rotated password on "invalid credentials," handle the forced-change screen if it's truly the first login) using `Promise.race` over three `waitFor` outcomes — plus `workers: 1` in `playwright.config.ts` (now explicit, not just `fullyParallel: false`) so spec files never interleave against the one shared emulator/account. `ADMIN_ROTATED_PASSWORD` is now exported from `playwright.config.ts` as the one shared source of truth for that literal, imported by both spec files.
- **The 10k-listing synthetic generator moved from a private test fixture to a genuine public subpath.** `packages/shared/package.json`'s `exports` map only ever listed `"."` — `__fixtures__/` (already private-by-convention, used only via relative imports *inside* `packages/shared`) is structurally **unreachable from any other workspace package** once an `exports` map exists (Node's resolution treats it as an allowlist). Cross-package reuse (the payload-budget test in `apps/server`, and the new `seed/seedSynthetic.ts`) needed a real subpath: added `"./testing": "./src/testing/index.ts"` to `packages/shared/package.json`, holding `buildSyntheticListings` (extracted from `apps/server/src/cache/payloadBudget.test.ts`, behaviour unchanged, that test now imports it) — excluded from `packages/shared`'s own `build` output (`tsconfig.build.json`) the same way `__fixtures__` is, since it's dev/test tooling, not a runtime dependency `apps/web` should ever see.
- **Hallmark skill invocation unavailable this session** (`Skill({skill: 'hallmark'})` → "Unknown skill: hallmark" despite `.claude/skills/hallmark/SKILL.md` existing on disk — likely a registration gap for this session, not a missing install; worth the next session checking whether it resolves). Applied the skill's own written principles manually instead, reading `references/anti-patterns.md` and `references/responsive.md` directly: `font-variant-numeric: tabular-nums` on every table/count column (gate against "tabular data without tabular-nums"), explicit `:hover`/`:active`/`:disabled` states added to every interactive element that only had `:focus-visible` before (cluster nav tabs, bucket tabs, toolbar selects/inputs — gate against incomplete state coverage), `white-space: nowrap` on every clickable affordance, a `@media (max-width: 30rem)` pass verified with zero horizontal page overflow at 320/375/414/1440px via `scrollWidth`/`clientWidth` checks in a real browser. Not a full audit against every gate in the skill (that's explicitly the hardening-phase's job per `FRONTEND.md` §5) — a reasonable, proportionate first pass for a data-dense dashboard surface with no hero/marketing content, where most of the skill's anti-patterns (gradient heroes, feature grids, aurora blobs) don't apply at all.
- No conflicts with the Specifications were encountered beyond the recorded `virtualScroller` deviation above; no Part A write path was touched; `regione`/`capoluogo`/`provincia`/`blocco` search keys are reserved (typed, round-trip-safe, `blocco` even already respected by `filterModel.ts`'s filter predicate) but have no UI control yet, matching the Phase 4/5 boundary confirmed against `PHASE_5_DRILLDOWN_OMI_ARCHIVE.md` before writing any code this phase.
