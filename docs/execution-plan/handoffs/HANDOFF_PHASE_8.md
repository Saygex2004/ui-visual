## 2. Notes, observations, implementation details

- **The domain engine (`domain/calendar.ts`'s `isEligibleForCalendar`/`diversifiedDraw`, `domain/priceBand.ts`, `domain/rng.ts`) already existed complete and tested from Phase 1.** This phase's real work was the Firestore transaction orchestration, routes, and client — not domain rules. The one domain-adjacent gap found and fixed was schema-level (see next point), not a rule bug.
- **`CalendarRowSchema` was missing `area` — a real gap, fixed additively.** A calendar day can mix immobili and corporate rows (admin by-id assignment is the *only* path corporate listings enter a calendar — DOMAIN_RULES §8 keeps automatic/random assignment immobili-only), so each row needs its own area for the workspace/quick-chat link to route correctly, unlike area-view tables which have one table-wide area. Added `area: AreaSlug` to the schema and a per-row fallback (`row.area ?? area`) in `DataTable.tsx`; proven end-to-end by the second e2e test (search → assign corporate id 2001 → navigate to its day → click "Scheda" → land on `/aste/crediti/lotto/2001`).
- **Two different concurrency guarantees, not one.** DATA_MODEL/SPECIFICATIONS only describe the same-user case explicitly (guarded by the deterministic `calendar_days/{user_id}_{date}` doc id). The different-users-racing-over-the-same-pool case needed its own guard: reading the full `assignment_index` collection **inside** the transaction, since Firestore retries a transaction whose *query* read set was invalidated by a concurrent commit, not just single-document reads. Both guarantees are proven by dedicated integration tests, not just reasoned about.
- **A real production bug caught by integration testing, not manual QA**: `FieldValue.arrayUnion()` throws when called with zero arguments. `randomAssign`'s "day already exists" branch called `arrayUnion(...drawn)` unconditionally; when the eligible pool was already exhausted (e.g., an 18-max auto-assign having claimed nearly the whole ~24-26-listing pool), `drawn` could be empty, and the call crashed with a 500. Fixed with an `else if (drawn.length > 0)` guard around that whole branch (`byIdAssign`/`removeAssignments` were already correctly guarded). Found via the admin integration test that flips `generated` to `'mixed'`.
- **Completed-count and the month view's "actionable" flag deliberately read from two different sources.** `completed` (day progress, month cell) uses `assignment_index.completed_at != null` — permanent, survives a later rating clear, per DATA_MODEL §11. `actionable` needs the **live rating value**, which `assignment_index` doesn't store (only a timestamp), so it's read from the current `ratings` collection instead. This means `actionable` can turn false after a rating is cleared even though the listing stays permanently "completed" — the only interpretation the data model supports, not a bug.
- **By-id assignment does not skip a listing that's "already assigned to someone else but not completed."** API_CONTRACT.md §7 names exactly two skip reasons (`not_found`, `completed`); since `assignment_index`'s doc id *is* the listing id, a by-id reassignment necessarily overwrites the existing entry. Read as a deliberate admin reassignment workflow (moving an uncompleted assignment from one team member to another) and covered by a dedicated integration test, not guarded against.
- **By-id search reads `listingsRepo.getByScope` directly, not the "active-only" snapshot cache** — the cache explicitly excludes archived listings, but by-id search's only two documented skip reasons (`not_found`, `completed`) don't exclude archived ones, so they must remain searchable.
- **`todayIso()` exists in two places with different, both-deliberate semantics.** The server's `repositories/calendar.ts` version uses UTC (no timezone config exists in this project) and is the sole authority for whether a requested `:date` triggers auto-assignment — the client's claim is never trusted. The client's pre-existing `features/dashboard/sessionArchive.ts` version uses the viewer's local calendar day (to avoid a midnight-boundary shift in positive-UTC-offset zones) and was reused as-is for `MonthView`'s "today" highlighting — a client-perspective concern the server doesn't need to share.
- **Another recurring cross-file e2e collision, this time caught proactively via calculation rather than reactively via a failure.** The seed fixture has only ~24-26 immobili listings actually eligible for automatic assignment, against an 18-listing draw — meaning listings 1055 (Pisa, `ratings-collaboration.spec.ts`'s exact-timeline-count target) and 1031 (Tivoli, `chat-collaboration.spec.ts`'s) had a high chance of being swept into any auto-assignment and gaining an extra `calendar_assigned` activity event. Fixed by naming the new file `zz-calendar-assignment.spec.ts` so it deliberately sorts **last** alphabetically — every other file's exact-count assertion runs and passes before today's calendar activity exists at all. Confirmed by the full-suite run in the verification results above. This is the same class of bug Phase 7 hit reactively (see `HANDOFF_PHASE_7.md` §2) on the listing-id axis rather than the file-ordering axis; **any future phase adding e2e coverage that touches automatic calendar assignment should keep this in mind** — either reserve specific listings the way 1055/1031 are now implicitly reserved, or apply the same `zz-` ordering trick.
- **The progress line is poll-driven and not invalidated by a rating mutation** — `DayView`'s `useDay` polls on `POLL_CADENCES_MS.calendarDay` (~20s) and is not force-refetched after a rating succeeds, the same deliberate "poll reconciles, no forced invalidation" pattern Phase 6 established for ratings elsewhere. The e2e test waits out one real poll cycle (`{timeout: 25_000}`) rather than treating the delay as a bug.
- No conflicts with the Specifications found or recorded this phase.
