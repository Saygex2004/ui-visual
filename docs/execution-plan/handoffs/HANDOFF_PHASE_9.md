## 2. Notes, observations, implementation details

- **A real, load-bearing correction: `@radix-ui/react-dialog@1.1.23` does NOT set `aria-modal` itself** — verified by reading the installed package's compiled source (`node_modules/.pnpm/@radix-ui+react-dialog@1.1.23.../dist/index.mjs`), not assumed from documentation. `DialogContentImpl` sets `role="dialog"` and conditionally `aria-labelledby`/`aria-describedby`, but no `aria-modal` anywhere in the bundle. The original plan (and this phase's first draft of `Dialog.tsx`) assumed Radix supplied it natively, matching how several Radix docs/examples describe the primitive; a manual browser check (`getAttribute('aria-modal')` on the live DOM node returning `null`) caught the gap before it shipped. Fixed by having `components/Dialog.tsx`'s `DialogContent` wrap `RadixDialog.Content` and set `aria-modal="true"` explicitly — this is now the one place in the whole migration that still needs a manual ARIA addition, mirroring (in miniature) the PrimeReact Drawer's own `role="complementary"` override this phase set out to eliminate. Any future Dialog usage in this codebase should go through `components/Dialog.tsx`, not `@radix-ui/react-dialog` directly, to keep this guarantee centralized.
- **Radix `Tabs.Content`'s "only the active tab is in the DOM" behaviour works differently than initially assumed, though the practical effect is the same.** Verified by reading `@radix-ui/react-tabs@1.1.21`'s compiled source and confirming live in a real browser: `Tabs.Content` always renders its own wrapper `<div role="tabpanel">` for **every** tab (hidden via the `hidden` attribute when inactive — this is intentional, ARIA APG expects a tabpanel element to exist per tab), but only renders that wrapper's **children** for the active tab. So a hidden, empty `role="tabpanel"` div persists per tab, but the expensive subtree (a `ClusterSection`'s `DataTable`, a bucket's virtualized rows) does not mount for inactive tabs — confirmed by counting `<table>`/`<tr>` elements live in the DOM while cluster/bucket tabs were switched: exactly one `<table>` existed at a time. This satisfies the actual performance invariant Phase 4 established, but the doc-comments in `components/Tabs.tsx`/`AreaView.tsx`/`ClusterSection.tsx` were corrected to describe the mechanism precisely (a persisting hidden wrapper, not a fully unmounted subtree) rather than repeat the imprecise "unmounted when inactive" framing the initial plan used.
- **The 1-row table in the manual verification screenshots is expected, not a regression.** Cluster 1 → "Procedure principali" in the seeded fixture data genuinely has exactly one matching listing under the current classification rules (the toolbar's own live count confirms "1 listing"); this phase touched no classification, filtering, or fixture-data code, only the UI library underneath, so this is pre-existing app behaviour, not something introduced here.
- **`PasswordInput`'s API is a deliberate, small simplification**, not a preserved 1:1 port: PrimeReact's `onValueChange={(e: {value: string | null}) => …}` headless-event convention became a plain `onChange={(value: string) => …}` callback. Every one of the 8 call sites was being edited in this same phase regardless (task 4 of the phase document explicitly calls for rolling out the new primitives everywhere), so there was no external caller to preserve the old shape for.
- **Zero custom CSS existed for Button/InputText/InputPassword before this phase** — confirmed by grepping every `.css` file under `apps/web/src` for `.p-button`/`.p-inputtext`/`.p-password` (zero hits) and confirming no call site ever passed a `className` prop to these three PrimeReact components. All of their pre-migration chrome (border, padding, radius, hover/focus states) came from PrimeReact's Aura styled-mode preset, remapped only for colour/focus-ring/surface tokens by the now-deleted `theme/preset.ts`. This phase therefore had to **author genuine new CSS** (`button.css`/`textInput.css`/`passwordInput.css`) against the existing cobalt tokens (`--color-accent`, `--radius-md`, `--color-focus`, etc.) to approximate the prior look — not a mechanical import swap over pre-existing project classes, as a literal reading of "same look, different implementation" might suggest. Manual visual inspection (screenshots, §1.8) confirms the result is clean and consistent with the existing token system, but it is a close approximation rather than a byte-for-byte visual clone of Aura's rendering (Phase 10's redesign supersedes this look regardless).
- No conflicts with the Specifications found or recorded this phase; no behaviour, route, or endpoint changed anywhere (grep/diff-reviewed against the constraint before writing the handoff).
