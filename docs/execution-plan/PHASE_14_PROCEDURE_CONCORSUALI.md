# Phase 14 — Procedura Concorsuale: New Part A Collection, Debtor-Facts Panel, Table Indicator

> Goal: read the new `procedure_concorsuali` Part A collection (`DATA_MODEL.md` §17), join it onto listings by court/registry number/year (`DOMAIN_RULES.md` §12), and surface it in the UI two ways: a debtor-facts panel in the workspace's Dettagli tab (mirroring the existing OMI panel) and a small presence indicator in every dashboard/archive/calendar table row. Post-launch feature work — read [`00_OVERVIEW.md`](00_OVERVIEW.md) and follow its session protocol; note its ordering note for how this phase differs from a pre-launch build phase.

## Preamble (assume zero prior context)

You are extending **`pvp-dashboard`**, a live-in-production TypeScript monorepo (pnpm workspaces: `apps/web` React+Radix SPA, `apps/server` Fastify+Zod API, `packages/shared` Zod schemas/domain rules) that reads a shared Cloud Firestore database kept current by a separate, independent scraper project. This phase adds a **fourth Part A collection**: `procedure_concorsuali`, the record of Italian insolvency procedures from a different scraper source (`portalecreditori.it`) than the one that writes `listings`/`omi_prices`. It is read-only here, exactly like every other Part A collection (`00_OVERVIEW.md` §5's compliance rule: no code path may ever write it).

**What makes this collection different from `omi_prices` (the closest existing precedent) and why that matters:**

1. **Not geography-keyed.** OMI is joined onto a listing by `(provincia, comune)`; this collection is joined by `(tribunale, numero, anno)` — the same tuple already load-bearing for blocco grouping (`DOMAIN_RULES.md` §6), minus `tipo_procedura` (the two sources spell it differently, so it's excluded from this join key — see `DOMAIN_RULES.md` §12).
2. **Not scope-restricted.** OMI only applies to `immobili` (real-estate) listings; a matching insolvency procedure is equally relevant to a `corporate` (credits/shares) listing from the same failed company. Fetch and join it for both scopes.
3. **Not on any refresh schedule.** `listings`/`omi_prices` are kept current by a scraper that runs on launchd, with `meta` documents this app polls for cache invalidation. This collection's source scraper is **run manually, on demand**, by its own operator, potentially days or weeks apart. There is no `meta/procedure_concorsuali` document and none should be invented — the collection simply gets picked up, stale-but-correct, whenever a scope's snapshot next rebuilds for any other reason (`DATA_MODEL.md` §17.3).
4. **Large relative to its emulator seed coverage.** ~23,900 real documents exist in production; the emulator's fixture dataset has none yet (out of this phase's scope to invent a representative fixture generator for a dataset this size — see Constraints). This phase's verification therefore includes a **read-only live smoke** against the real collection, the same accepted exception Phase 4 used for its own optional live read.
5. **Carries personal data.** `debitore.codice_fiscale` identifies a natural person for individual debtors. Nothing in this phase's UI work changes how carefully that should be handled — it renders in the same auth-gated workspace as every other listing fact, never in a public or unauthenticated surface.

**State when this phase starts:** Phases 0–13 complete and live in production (`git log` on `easter-eggs` shows the Phase 12 go-live commit plus post-launch commits). `procedure_concorsuali` exists in the real Firestore project with real data (verify via the entry criteria) but nothing in this codebase reads it yet.

## Tasks

1. **Domain module** (`packages/shared/src/domain/procedureConcorsuali.ts`, exported from `domain/index.ts`), pure, mirroring `omi.ts`'s structure:
   - `tribunaleKey(name: string | null): string` — the `DOMAIN_RULES.md` §12 normalization (NFKD accent strip, `"Tribunale (ordinario) di"` / `"Tribunale di"` prefix strip, uppercase, whitespace collapse) plus the two-row override table, exported as a `PROCEDURA_TRIBUNALE_OVERRIDES` constant so it's independently testable and documentable, matching the pilot's own already-shipped table verbatim (do not re-derive it — it's specified in full in `DOMAIN_RULES.md` §12).
   - `proceduraMatchKey(tribunale: string | null, numero: string | null, anno: string | null): string | null` — the listing-side key; `null` (never a partial key) if any input is `null`, same discipline as `bloccoKey`.
   - `ProceduraConcorsualeDoc` interface (server-side raw shape: `id`, `nome`, `rg` incl. `numero_base`/`anno`, `tipo_code`, `tipo_procedura`, `tribunale.{nome,chiave}`, `professionista`, `giudice_delegato`, `debitore.*`, `link`, `estratto_il`, `scheda_letta_il`).
   - `proceduraDocKey(doc: ProceduraConcorsualeDoc): string | null` — the same key shape, built from the **document's own already-normalized** `tribunale.chiave`/`rg.numero_base`/`rg.anno` fields (no re-normalization needed on this side).
   - `ProceduraConcorsualeSelection` (display shape: everything the workspace panel needs) and `selectProceduraConcorsuale(byKey: Readonly<Record<string, ProceduraConcorsualeDoc>>, params: { tribunale: string | null; numero: string | null; anno: string | null }): ProceduraConcorsualeSelection | null` — looks up `proceduraMatchKey(...)` in the map; returns `null` on no match or any null input. No two-tier fallback (unlike OMI's province-capital fallback) — this is an exact-key join only.
   - `hasProceduraConcorsuale(byKey, params): boolean` — the table-row flag, a thin wrapper so `toListingRow` doesn't need to know the full selection shape just to compute a boolean.
2. **Pure-logic tests** (`packages/shared/src/domain/procedureConcorsuali.test.ts`), matching `blocco.test.ts`/`omi.test.ts`'s depth: `tribunaleKey` accent/prefix/override cases (the exact `Forlì`, `"Tribunale (ordinario) di X"`, both override-table rows, from `DOMAIN_RULES.md` §12 verbatim); `proceduraMatchKey`/`proceduraDocKey` null-in-any-field → `null`; `selectProceduraConcorsuale` match / no-match / `scheda_letta_il`-still-null cases; `hasProceduraConcorsuale` true/false.
3. **Schemas** (`packages/shared/src/schemas/partA/proceduraConcorsuale.ts`, mirroring `omiPrice.ts`): `ProceduraConcorsualeSchema` (`.passthrough()`, every field from `DATA_MODEL.md` §17's table, nested `rg`/`tribunale`/`debitore` objects, `estratto_il: instant`, `scheda_letta_il: instant.nullable()`). Extend `schemas/api/snapshot.ts`'s `ListingRowSchema` with `has_procedura_concorsuale: z.boolean()`; add a `ProceduraConcorsualeEntrySchema` there (or a new small schema file) for the display shape (`nome`, `tipo_code`, `tipo_procedura`, `professionista`, `giudice_delegato`, `debitore` nullable object, `link`, `available: z.boolean()` — `available` mirrors OMI's semantics but means "`scheda_letta_il` is set", not "no error"); extend `schemas/api/listingDetail.ts`'s `ListingDetailSchema` with `procedura_concorsuale: ProceduraConcorsualeEntrySchema.nullable()`.
4. **Repository** (`apps/server/src/repositories/procedureConcorsuali.ts`), cloning `omiPrices.ts`'s `getAllBySlug` shape exactly, but keyed by `proceduraDocKey(doc)` instead of a comune slug (skip a document whose key comes back `null` — an unparseable/incomplete source record, log at debug, never throw); register as `procedureConcorsualiRepo` in `repositories/index.ts`'s Part A read-only block.
5. **Cache wiring** (`apps/server/src/cache/build.ts`, `cache/rows.ts`, `cache/cache.ts`): fetch `procedureConcorsualiRepo.getAllByKey(db)` in `buildSnapshot`'s existing `Promise.all` **unconditionally** (both scopes, not `isImmobili`-gated like OMI); thread the map through `assembleSnapshot` (new parameter) into `toListingRow` (sets `has_procedura_concorsuale` via `hasProceduraConcorsuale`) and store it on `BuiltSnapshot`/`ScopeState` as `proceduraByKey` (mirroring `omiBySlug`); add `SnapshotCache.selectProcedura(tribunale: string | null, numero: string | null, anno: string | null): ProceduraConcorsualeSelection | null`, a synchronous zero-Firestore-read lookup like `selectOmi`, **not scope-gated**.

## Constraints

- **Read-only, structurally.** No function in `repositories/procedureConcorsuali.ts` or anywhere else may create/update/delete a `procedure_concorsuali` document — mirrors every other Part A collection's guarantee.
- **No `meta/procedure_concorsuali` document invented.** Do not add polling/invalidation machinery for this collection — it deliberately rides the existing rebuild cadence (`DATA_MODEL.md` §17.3). If a faster-refresh need emerges later, that is a future phase's decision, not this one's.
- **Not a full-collection browse/search screen.** This phase is enrichment-only (workspace panel + table flag) — explicitly out of scope per the product decision behind this phase; do not build a standalone "browse all procedure_concorsuali" route even though the data would support one.
- **No emulator seed fixture for this collection is required by this phase** — generating a representative ~24k-document (or even a small hand-picked) fixture set for the seed script is a reasonable future improvement but is not blocking; the live smoke (task 10) is the accepted substitute, same precedent as Phase 4's optional live read. Do not skip the live smoke to avoid this — it is this phase's actual proof the feature works against real data.
- **`debitore.codice_fiscale` is personal data** — nothing new to build for this (the workspace is already auth-gated), but do not add any code path that could surface it outside the authenticated workspace (e.g. no server log line printing full debtor records, no client-side console.log left in).
- **All copy in Italian, externalized** (`00_OVERVIEW.md` §5) — no exception for a "small" feature.
